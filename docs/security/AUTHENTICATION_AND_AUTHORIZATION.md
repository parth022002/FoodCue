# FoodCue — Authentication & Authorization Specification

This document details the identity, authentication, session management, and multi-tenant authorization architecture of FoodCue.

---

## 1. Authentication Architecture (Clerk React Core 3)

FoodCue integrates **Clerk** for user authentication and multi-tenant organization management.

### 1.1 Zero-Account Guarantee
- FoodCue initializes in **Guest Mode** by default.
- All core scanner, health score, local pantry, and shopping list functions execute locally in IndexedDB without requiring an account.
- Users only encounter Clerk if they explicitly click **Sign In** in the topbar or navigate to **Family Sharing**.

### 1.2 Frontend Integration
- **Wrapper:** `<ClerkProvider publishableKey={import.meta.env.VITE_CLERK_PUBLISHABLE_KEY}>` in `src/main.tsx`.
- **UI Components:**
  - `<SignInButton />` & `<SignUpButton />` for modal sign-in.
  - `<UserButton />` for managing profile, email, and connected sessions.
  - `<OrganizationSwitcher />` for switching between Personal mode and active Household Organizations.
- **Hooks:**
  - `useUser()`: Access user ID, email, profile details.
  - `useOrganization()`: Access active household ID, name, role (`admin` or `member`), and members count.

## 2. Server-Side Token Verification

All protected serverless routes (`/api/me`, `/api/devices`, `/api/sync/*`, `/api/notifications/*`) verify the caller's identity:

```typescript
import { createClerkClient } from "@clerk/backend";

const clerk = createClerkClient({ secretKey: process.env.CLERK_SECRET_KEY });

export async function authenticateRequest(req: Request) {
  const authHeader = req.headers.get("authorization");
  if (!authHeader?.startsWith("Bearer ")) {
    throw new Error("Missing or invalid Authorization header");
  }
  const token = authHeader.split(" ")[1];
  const session = await clerk.authenticateRequest(req);
  return session;
}
```

## 3. Cryptographic Webhook Synchronization (Svix)

User lifecycle events are synchronized from Clerk to Neon PostgreSQL via `POST /api/webhooks/clerk`:

### 3.1 Svix Signature Verification
Every webhook request is cryptographically validated using `CLERK_WEBHOOK_SIGNING_SECRET`:
- `svix-id`: Unique message ID (used for idempotent deduplication).
- `svix-timestamp`: Request timestamp (mitigates replay attacks within a 5-minute tolerance window).
- `svix-signature`: HMAC-SHA256 signature generated by Svix.

### 3.2 Handled Events
- `user.created`: Inserts a new user record into `foodcue_users`.
- `user.updated`: Updates profile name, email, or avatar in `foodcue_users`.
- `user.deleted`: Cascades or anonymizes user records according to GDPR/DPDPA data deletion rules.
